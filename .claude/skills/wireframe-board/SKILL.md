# wireframe-board — доска каркасов до стиля

Делает **одну HTML-страницу**, на которой лежат все экраны продукта сразу: серые каркасы 264×540 рядами по потокам, у каждого подпись и маркер потока. Открывается двойным кликом, скроллится как доска, показывается на экране целиком. Это первая картинка проекта: структура уже видна, стиля ещё нет.

## Когда использовать

После флоу и до дизайн-системы. Задача доски — ответить на вопросы «что на экране, в каком порядке, что здесь главное и куда ведёт каждый элемент», пока их не замаскировал стиль. Ошибка структуры здесь стоит минуты, на этапе кода стоит дни.

Не использовать: для макетов в Figma, для готового UI по дизайн-системе (там `flow-to-app`), для схемы навигации без экранов (там `ia-first`).

## Что лежит в скилле

- `board.css` — кит: палитра, размеры экрана, все примитивы. **Размеры и цвета не выдумывать, брать отсюда.**
- `template.html` — скелет доски: шапка, принципы, легенда потоков, карта навигации, секция с тремя паттернами экранов.

## Алгоритм

### 1. Поставить доску
```
cp <папка скилла>/board.css <проект>/design/board.css
cp <папка скилла>/template.html <проект>/design/wireframes.html
```
Дальше правится только `wireframes.html`.

### 2. Собрать шапку
Шапка задаёт рамку чтения и делает доску самодостаточной:

- `h1` — «Продукт — вайрфреймы».
- `.sub` — одна фраза про продукт, потом паттерн-референсы («анатомия карточки от Tinder, сетка поиска от Behance, визард от Airtasker»), и обязательная закрывающая фраза: **это структура, не визуальный стиль**. Без неё доску начнут обсуждать как дизайн.
- `.princ` — три-пять чипсов с продуктовыми принципами, которые видно в каркасах («работа это первый экран человека», «общение в ТГ, не в аппке»).
- `.legend` — потоки с цветными точками, до четырёх. Поток это сквозной сценарий, а не таб.
- `.map` — карта в одну строку: откуда приходят → продукт с табами → чем заканчивается.

### 3. Разложить экраны
Одна `<section>` = один поток или один таб: `h2` + одно предложение зачем + `.row` из ячеек.

Ячейка это всегда пара: `.phone` (экран) + `.cap` (подпись). **Подпись обязательна у каждого экрана**, без исключений: код, название, одно-два предложения о том, что здесь важно в структуре.

Коды экранов сквозные и говорящие (`ONB-2`, `F1`, `SEARCH-PEOPLE`), чтобы из карты навигации и из кода можно было сослаться на конкретный каркас.

Маркер потока (`.flows` с цветной точкой) ставится на каждый экран. Экран без маркера означает, что он не участвует ни в одном сценарии, и это повод его выкинуть.

### 4. Паттерны экранов
В шаблоне лежат три, ими закрывается почти всё:

- **Стек блоков** — обычный экран: `.bar`/`.txt` вместо текста, `.field`, `.chip`, `.btn`, снизу `.tabbar`.
- **Full-bleed медиа** — карточка с контентом во весь экран: `.work` (штриховка вместо картинки), `.segs` (пагинация), `.tapzone` (зоны тапа), `.grad` (инфо на градиенте), `.actions` с `.fab`.
- **Оверлей** — момент-событие поверх экрана: `.overlay` + `.modal`.

Остальные примитивы кита: `.avatar`, `.seg2` (сегменты), `.case`/`.gcard` (карточки контента), `.conn` (строка списка), `.toggle`/`.setrow` (настройки), `.bub` (сообщение бота), `.ice` (заготовка текста), `.overlay`, `.hr`, `.note`.

### 5. Дописать логику
Последняя секция — то, что не видно на каркасах: правила выдачи и подмешивания, приоритеты, лимиты, пустые состояния. Текстом, без экранов. Иначе эти решения потеряются между флоу и кодом.

### 6. Проверить
Открыть доску в браузере и пройтись глазами:
- у каждого экрана есть подпись и маркер потока;
- по каждому потоку читается непрерывная цепочка, от входа до результата;
- у каждого интерактива на каркасе понятно, куда он ведёт (иначе вернуться в `ia-first`);
- есть пустые состояния и состояния ошибки, не только счастливый путь;
- экраны одной секции стоят в порядке прохождения, а не как попало.

## Правила

1. **Ноль стиля.** Только серо-бежевая палитра кита. Бренд, цветные кнопки, шрифты, иконки, тени не появляются. Цвет на доске имеет ровно одно значение: номер потока.
2. **Текст плейсхолдерами, смысл словами.** Абзацы это `.bar` и `.txt`, но ключевые надписи (заголовок экрана, лейбл кнопки, интент) пишутся настоящими словами: по ним и читается структура.
3. **Медиа штриховкой.** Любая картинка это `.work`, внутри `.wlabel` с описанием, что там лежит. Реальные изображения на доску не кладут.
4. **Один экран — одно состояние.** Заполненное и пустое, до и после действия это разные ячейки, а не один экран с оговоркой в подписи.
5. **Жесты подписываются.** Если экран листается тапом по краю или свайпом, это видно (`.tapzone`) и сказано словами в градиенте или подписи.
6. **Курсив не используем.**

## Чек-лист

- [ ] `board.css` рядом, размеры и цвета не переопределены в разметке
- [ ] Шапка: продукт, паттерн-референсы, фраза «это структура, не визуальный стиль»
- [ ] Принципы чипсами, потоки в легенде, карта навигации в строку
- [ ] Секции по потокам, внутри порядок прохождения
- [ ] У каждого экрана: код, подпись, маркер потока
- [ ] Есть пустые состояния и ошибки
- [ ] Последняя секция с невидимой логикой
- [ ] Прокликано в браузере, ни один интерактив не ведёт в никуда

## Не делать

- Не рисовать по одному экрану в отдельных файлах: ценность доски в том, что всё видно рядом.
- Не заводить пятый цвет потока: больше четырёх сквозных сценариев значит, что продукт не помещается в одну доску, надо резать скоуп.
- Не украшать каркасы, чтобы «показать заказчику красиво»: как только появляется стиль, обсуждение уходит с структуры на цвет кнопки.
- Не пропускать подписи: доска без них читается только автором.
